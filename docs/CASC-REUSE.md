# Обновление клиента с повторным использованием данных

С версии 1.4.14 лаунчер умеет собирать опубликованный снимок из локальных
блоков и HTTP Range-загрузок. Это не редактирование локальных CASC-индексов
и не сравнение размеров архивов.

## Алгоритм

1. Манифест содержит необязательный `reuse_manifest`: URL, размер и SHA-256
   карты блоков. Карта привязана к `data_revision` и итоговым хешам архивов.
2. Архивы `Data/{data,ecache,wowf}/data.NNN` разбиваются по содержимому
   алгоритмом `gear-v1`: min 64 КиБ, средний размер около 320 КиБ,
   max 1 МиБ. Формат и константы одинаковы у генератора и лаунчера.
3. Лаунчер читает локальные архивы и строит индекс SHA-256 → файл/смещение.
   Локальные `.idx` не используются. Смещение и имя архива могут отличаться.
4. Данные копируются в отдельный staging-файл. При копировании SHA-256
   проверяется ещё раз, чтобы не доверять изменившемуся после чтения источнику.
5. Соседние недостающие блоки объединяются в запросы до 8 МиБ. Ответ должен
   иметь HTTP 206 и точный Content-Range, каждый блок проверяется по SHA-256.
6. Проверяется итоговый SHA-256 всего собранного архива. Только после подготовки
   всего комплекта выполняется прежняя замена Data целиком.

Мелкие файлы и бинарники тоже копируются локально, если их итоговый SHA-256
совпадает. Индексы ставятся из снимка при замене Data и затем не сверяются
по старым именам. WTF и аддоны не затрагиваются.

## Ограничения

- Нужно прочитать старые данные, записать и проверить новый набор; это работа
  диска, даже когда трафик мал. Для staging по-прежнему нужно около 56 ГБ.
- Объём докачки зависит от фактических локальных байтов. При иной компрессии,
  сильной перестановке мелких записей, повреждении или отсутствии старых данных
  доля совпадений уменьшается. Гарантировать одинаковую экономию всем нельзя.
- Полностью готовые staging-архивы используются после прерванного обновления.
  Незавершённый архив собирается повторно; повторная загрузка части блоков
  этого архива возможна. Старый клиент при этом остаётся нетронутым.
- Без карты блоков остаётся прежний путь полной загрузки. При ошибке карты
  или неправильном Range-ответе обновление останавливается, а не незаметно
  переключается на загрузку 56 ГБ. При отсутствии подходящих локальных
  архивов применяется обычная параллельная загрузка.
- Алгоритм переиспользует байтовые блоки, а не декодированные ресурсы игры:
  он не требует ключей расшифровки BLTE и не перепаковывает данные Blizzard.

## Подготовка и проверка карты

```bash
cd /root/launcher/app/src-tauri
cargo run --release --example casc-reuse -- generate \
  /opt/forever/releases/client-70888-20261113 \
  /srv/forever-launcher/manifest.json /root/backups/reuse-gear-v1.json

# Оценка совпадений, только чтение исходного клиента:
cargo run --release --example casc-reuse -- audit \
  /opt/forever/client /root/backups/reuse-gear-v1.json /root/backups/reuse-audit.json

# Реальная сборка каждого архива, докачка диапазонов, итоговый SHA-256.
# Каталог должен быть новым. Проверенные временные архивы удаляются по одному,
# поэтому для этой серверной проверки не требуется ещё одна полная копия.
cargo run --release --example casc-reuse -- verify \
  /opt/forever/client /root/backups/reuse-gear-v1.json /var/tmp/reuse-verification
```

Публиковать карту только после выпуска Windows/SteamOS 1.4.14 и проверки:

```bash
python3 /root/wowserver/scripts/attach-client-reuse.py /root/backups/reuse-gear-v1.json
```

Скрипт сверяет покрытие всех архивов, их размеры и SHA-256, публикует карту
под именем с хешем и добавляет ссылку в манифест. `data_revision` не меняется:
игроки с уже установленным снимком не обязаны заново восстанавливать клиент.
