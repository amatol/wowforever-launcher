# Yandex Disk как источник клиента

Статус: **Yandex-only подготовлен для 1.4.29, но пока НЕ опубликован.**
Живая 1.4.28 использует гибридную схему ниже. Переключение заблокировано:
четыре файла Data/indices на Yandex возвращают HTTP 500 при скачивании.
До восстановления файлов существующие серверные копии и живые манифесты
не удалять и не менять.

Публичная папка:
`https://disk.yandex.ru/d/DxjZXLCwnEimiw`, каталог `/1.60.1.70938`.

## Что где лежит сейчас (живая 1.4.28, до переключения)

- **Yandex Disk:** 47 архивов `Data/data/data.*` (около 50,4 ГиБ).
  Это тяжёлая часть клиента, на VDS она не хранится и не раздаётся.
- **Наш сервер** (`/launcher/files-70938/`, каталог
  `/srv/forever-launcher/files-70938`): `.build.info`, `_forever_/`,
  `Data/config`, `Data/indices`, `Data/wowf`, `Data/ecache`. Сюда входят
  `Wow.exe` и `wow_loader.dll`; в живой 1.4.28 они скачиваются с нашего сервера.
- **Манифесты:** `manifest.json` (список файлов и SHA-256) и
  `client_build.json` (требуемая сборка, блок `yandex`, список `overlay`).

## Порядок источников в лаунчере

- В подготовленной 1.4.29 **все** файлы клиента идут только с Yandex:
  `.build.info`, EXE, DLL, индексы, конфиги и data.*. Overlay больше
  не исключает файлы из Yandex. Fallback на VDS/CDN отключён даже при
  некорректных параметрах включённого Yandex-источника.
- После переключения на VDS остаются только манифесты, конфигурация,
  новости, сертификат и файлы обновления самого лаунчера, но не клиента.
- Временный `href` Yandex API разрешается непосредственно перед каждой
  попыткой скачивания; в манифесте временные ссылки не хранятся.
- С лаунчера 1.4.23 действуют таймауты: 30 секунд на соединение и
  120 секунд на чтение очередного блока. Зависший источник считается
  ошибкой и повторяется, а не блокирует обновление навсегда.
- С лаунчера 1.4.25 ошибки скачивания повторяются автоматически: пауза
  5 секунд, до 50 повторов на каждый файл. Уже скачанные файлы остаются
  в staging, поэтому повтор продолжает установку, а не начинает её заново.
- Размер и SHA-256 проверяются после каждой загрузки.

## Первый переход и обновления

- 1.4.29 собирает целый согласованный набор в staging, без diff-карт.
  Для `Data/data/data.NNN` размер и SHA-256 локального файла сверяются
  с актуальным манифестом. Совпавший архив копируется в staging и повторно
  хешируется; отличающийся или отсутствующий скачивается целиком с Yandex.
  Одного номера сборки недостаточно. Индексы так не переиспользуются.
  Старые файлы не заменяются до готовности всего набора.
- Лаунчер скачивает весь набор (включая `Data/data/*.idx`) в скрытую
  папку `.forever-update-<версия>` внутри папки клиента и проверяет
  SHA-256 каждого файла. Затем он
  заменяет только игровые каталоги `Data` и `_forever_`, не переименовывая
  корневую папку клиента. Это важно, если в ней лежит запущенный лаунчер
  или файлы заняты антивирусом/Explorer.
- С 1.4.28 сохраняются как корневые `WTF/`, `Interface/`, так и игровые
  `_forever_/WTF/`, `_forever_/Interface/`: перед заменой вложенные папки
  копируются в новый `_forever_`. Дополнительно создаётся независимый
  резерв в `.forever-user-backups/<время>/`, который не удаляется автоматически.
  Ошибка резервирования останавливает замену. Символические ссылки требуют
  ручной проверки и не разыменовываются при резервировании.
- Старые staging-папки не удаляются автоматически: в них могут остаться
  пользовательские файлы после ошибок предыдущих версий.
- В `--play` показываются текущий этап, общий процент, имя файла и процент
  его загрузки (при параллельной загрузке — для последнего активного файла).
- Все этапы (старт, прогресс, повторы, ошибки, замена каталогов)
  пишутся в «Журнал» лаунчера и сохраняются между перезапусками.
- Для установки нужно свободное место на полный клиент (около 54 ГБ),
  потому что новая копия готовится в `.forever-update-<версия>` внутри
  папки клиента. После успеха старая
  копия удаляется.
- В `client_build.json` это включает флаг `"full_reinstall": true`.
- `Data/data/*.idx` входят в манифест: без них клиент не находит ROOT и
  ENCODING внутри `data.*` и сообщает о повреждённых файлах. После запуска
  игра может менять эти индексы; лаунчер их не перепроверяет.

## Генерация релиза

Обновлённый скрипт `scripts/yandex-client-release.py` обходит публичную папку,
стримит ВСЕ файлы через SHA-256 и MD5 без сохранения клиента на VDS и пишет
`manifest-70938.json` + `client_build_70938.json`. HTTP URL всех файлов пустые,
overlay пуст, минимальный лаунчер — 1.4.29. Прогресс сохраняется в
`manifest-70938.json.progress.json`, поэтому прерванный запуск
продолжается с места остановки. Кеш действителен только при совпадении размера
и MD5 с метаданными Yandex; старый кеш без MD5 требует повторного хеширования.

Пример:

```bash
python3 scripts/yandex-client-release.py \
  --version 20261116-3 --build 1.60.1.70938 \
  --source-path /1.60.1.70938 \
  --output /srv/forever-launcher/manifest-70938.json \
  --previous-manifest /srv/forever-launcher/manifest.json \
  --workers 4
```

Особенность сервера: Yandex перенаправляет загрузку на
`mds.storage.yandex.net`, а AAAA-запросы через системный resolver иногда
зависают. Скрипт принудительно использует IPv4 для `getaddrinfo`.

## Ограничения

- Yandex Disk — не CDN; возможны лимиты API, скорости и массовых загрузок.
  При 500 от API скрипт делает несколько попыток и повторный проход.
- Публичная ссылка должна быть стабильной; при её смене нужен новый
  `client_build.json`.
- Манифест и SHA-256 остаются на нашей стороне, иначе публичную папку
  можно подменить.
- До включения восстановить доступность четырёх Yandex-объектов:
  `Data/indices/0d18f5a5fea3c0f28e35118a22eed0bf.index`,
  `Data/indices/184a650b2ddde3e669ea8e5074e76439.index`,
  `Data/indices/a94ca0dd1dea7fbc4189fb047ae00b7a.index`,
  `Data/indices/e353ca95b78f9ead4290b49c65a19d63.index`.
  Проверка 16.11.2026: API выдаёт href, но скачивание завершается HTTP 500.
  Старый KO.PAK теперь скачивается с Yandex успешно.
